# SpendObserver — Android (Kotlin / Compose / Room)

Нативный Android-порт [SpendObserver](../expenses-tracker) — трекера доходов/расходов.
Полностью локальное приложение: без сервера, без сети, все данные хранятся в
SQLite-базе (через Room) внутри песочницы приложения на устройстве.

Оригинальный веб-проект (Next.js + IndexedDB) остаётся источником истины по
бизнес-логике, модели данных и UX — этот проект переносит их на нативный стек,
а не копирует реализацию 1:1.

## Согласованный стек

| Слой | Технология | Почему |
|---|---|---|
| Язык | Kotlin | стандарт Google для Android, меньше boilerplate, корутины |
| UI | Jetpack Compose | декларативный UI, ближе всего по духу к текущему React-коду |
| Хранение | Room (поверх SQLite) | надёжные транзакции, индексы, агрегатные запросы — аналог IndexedDB-слоя |
| Асинхронность | Kotlin Coroutines + Flow | стандартный способ работать с Room и состоянием экрана |
| Архитектура | MVVM + Repository | ViewModel + StateFlow на экран, Repository оборачивает DAO |
| Навигация | Navigation Compose | переходы между списком трекеров, трекером, графиками, настройками |
| Графики | Vico (Compose-native charting) | активно поддерживается, из коробки работает с Compose |
| DI | ручной Container на первом этапе, Hilt — опционально позже | не усложнять, пока не появится реальная необходимость |
| Тесты | JUnit4/5, Room in-memory DB, Turbine (Flow-тесты), Compose UI Test | аналог текущих 198 vitest-тестов |

## Что переносим из оригинала (feature parity)

Смотри `../expenses-tracker/README.md` и `CLAUDE.md.local` для деталей реализации.

- **Трекеры**: несколько независимых трекеров (личный/семейный/рабочий), каждый
  со своими тегами, годами, месяцами, записями.
- **Записи**: тип `income`/`cost`, сумма (хранится как целое число — центы),
  дата, один или несколько тегов, необязательное описание.
- **Калькулятор в поле суммы**: инлайн-вычисление выражений вида `120+50/2`.
- **Теги**: создание, переименование, удаление; общие в рамках трекера,
  применимы к нескольким записям сразу.
- **Графики**: разбивка доходов/расходов по тегам, количество записей по тегам,
  самые частые/самые дорогие теги, навигация по годам/месяцам, overview с
  фильтрацией по тегам.
- **Импорт/экспорт**: экспорт трекера в JSON-файл, импорт с выбором
  слияния/замены, перенос данных между устройствами через файл или "Поделиться".
- **Локализация**: en / ru / fr.
- **Валидация**: проверка структуры данных при импорте с локализованными
  сообщениями об ошибках.

## Отличия от оригинальной (IndexedDB) модели

В оригинале `Tracker → Year → Month → Record` — иерархия хранится буквально
(отдельные object store на годы/месяцы), а `totalAmount` денормализован и
пересчитывается вручную на каждом уровне.

В Room это избыточно: года и месяцы — это просто способ группировки записей
по дате, а суммы — это агрегатные SQL-запросы (`SUM(amount) ... GROUP BY`).
Планируемая схема:

```
Tracker      (id, title, createdAt, updatedAt, backupAt)
Tag          (id, trackerId, name)
Record       (id, trackerId, epochDay, type, description, amountCents)
RecordTag    (recordId, tagId)        // связь многие-ко-многим
```

Год/месяц/итоги по трекеру, по году, по месяцу, по тегу — вычисляются
запросами (`@Query` в DAO) или на лету во ViewModel, а не хранятся как
отдельные сущности. Это уменьшает количество таблиц и убирает целый класс
багов синхронизации денормализованных сумм, которые были в оригинале.

## План работ (этапы)

1. **Инициализация проекта**
   - Создать проект в Android Studio (Empty Activity, Compose, min SDK 26).
   - Подключить зависимости: Room, KSP, Navigation Compose, Vico, Coroutines.
   - Настроить пакет, тему (Material 3), базовую структуру папок выше.

2. **Слой данных**
   - Описать Room-сущности (`Tracker`, `Tag`, `Record`, `RecordTag`) и DAO.
   - Миграции Room (schema export) с первого дня, даже при единственной версии.
   - `AppDatabase` (singleton), `Repository` поверх DAO, экспонирующий `Flow`.
   - Тесты DAO на in-memory Room БД.

3. **Domain-слой**
   - Порт бизнес-правил из `src/lib/utils` оригинала: расчёт сумм, парсинг дат,
     калькулятор выражений (`calcExpression`), валидация импорта.
   - Unit-тесты на чистые функции (без Android-зависимостей).

4. **Список трекеров + создание/загрузка**
   - Экран со списком трекеров, создание нового, удаление, переименование.
   - ViewModel + StateFlow, первая end-to-end связка UI → Repository → Room.

5. **Экран трекера (accordion год/месяц/запись)**
   - Список записей, сгруппированный по году/месяцу (агрегатные запросы).
   - Итоги по году/месяцу/трекеру.

6. **Создание/редактирование записи**
   - Форма: сумма (с калькулятором), тип, дата, теги (мультивыбор), описание.
   - Управление тегами (создание на лету, переименование, удаление).

7. **Графики**
   - Интеграция Vico: доходы/расходы по тегам, топ тегов, overview с фильтром.

8. **Импорт/экспорт**
   - Экспорт трекера в JSON через Storage Access Framework
     (`ACTION_CREATE_DOCUMENT`).
   - Импорт через `ACTION_OPEN_DOCUMENT` с валидацией и выбором merge/replace.
   - "Поделиться" файлом через `Intent.ACTION_SEND`.

9. **Локализация**
   - `values/strings.xml`, `values-ru/strings.xml`, `values-fr/strings.xml` —
     перенос текстов из `src/locales/{en,fr,ru}.json` оригинала.

10. **Полировка**
    - Тёмная тема, иконка приложения, splash screen.
    - Compose UI-тесты на ключевые флоу (создание записи, импорт/экспорт).
    - Подпись и сборка `.apk`/`.aab`.

## Совместимость данных с веб-версией

Требование: файл, экспортированный из веб-приложения, должен без потерь и
без ручных преобразований импортироваться в Android-приложение — и наоборот.
Это значит, что формат JSON-файла экспорта — общий контракт между двумя
приложениями, а не деталь реализации одного из них.

### Канонический формат файла трекера

Текущий формат (веб, `src/lib/utils/fileContentHelper.ts` +
`src/lib/types/dataTypes.ts`):

```json
{
  "meta": {
    "id": "Family",
    "title": "Family",
    "createdAt": "15/01/2026_10:30:00",
    "updatedAt": "29/08/2026_18:02:00",
    "backupAt": "29/08/2026_18:05:00"
  },
  "tags": { "1": "groceries", "2": "rent" },
  "years": {
    "2026": {
      "id": 2026,
      "totalAmount": 154000,
      "months": {
        "1": {
          "id": 1,
          "title": "january",
          "totalAmount": 45000,
          "records": [
            {
              "id": 7,
              "year": 2026,
              "month": 1,
              "day": 15,
              "type": "cost",
              "tags": [1],
              "description": "weekly shopping",
              "amount": 5000
            }
          ]
        }
      }
    }
  },
  "totalAmount": 154000
}
```

Ключевые правила формата, которые Android-версия обязана соблюдать:

- **`meta.createdAt`/`updatedAt`/`backupAt`** — строка `dd/MM/yyyy_HH:mm:ss`
  (день **первый**, с секундами), а не `MM/dd/yyyy_HH:mm`, как можно
  неверно прочитать из примера выше по невнимательности — это реальный
  формат `formatDatetoMeta`/`parseMetaToDate` из `src/lib/utils/dateParser.ts`
  оригинала, побитово. Расхождение здесь ломает совместимость файлов между
  вебом и Android, так что при портировании ориентируйся на код, а не на
  словесное описание.
- **Суммы** — целые числа в центах (`amount`, `totalAmount`), никогда `Float`.
- **`month.title`** — фиксированный английский ключ месяца (`"january"` …
  `"december"`), не переведённая строка. Отображаемое имя месяца всегда
  выводится через локализацию по числовому `id`, а не берётся из этого поля.
- **`tags`** — словарь `{ "числовой id тега": "название" }`, ссылки на теги в
  записях (`record.tags`) — массив тех же числовых id.
- **Числовые id (`tags` ключи, `year.id`, `month.id`, `record.id`)** —
  внутренние идентификаторы БД-источника (в IndexedDB — автоинкремент), они
  **не являются устойчивым кросс-приложенческим ключом**. Room на Android
  использует свои собственные автоинкрементные PK, поэтому при импорте эти
  числа нельзя писать в БД как есть — нужно:
  1. Разобрать JSON в память, сохраняя связи по исходным id (какой tag id
     на какую запись ссылается).
  2. Создать теги заново, сопоставляя по **имени** (`tags` словарь) — если
     тег с таким именем уже есть в трекере, переиспользовать его id, иначе
     создать новый.
  3. Создать записи с новыми Room-id, подставив в `RecordTag` уже
     пересчитанные (новые) id тегов.
  4. То же самое в обратную сторону при экспорте из Android в JSON — Room-id
     мапятся на плотную нумерацию, начиная с 1, в тот же словарь `tags`.
- **`meta.id` / `meta.title`** — в вебе это одно и то же (пользователь вводит
  название трекера, оно же используется как имя IndexedDB-базы). Room-версия
  хранит трекер под собственным internal PK и просто использует `title` как
  отображаемое имя; при экспорте `meta.id` формируется как `title`.
- **Валидация при импорте** — Android обязан принимать файл, если в нём есть
  все поля из примера выше с правильными типами; лишние ключи в `meta`
  (текущий веб-валидатор их пока отклоняет) на Android-стороне не должны
  ронять импорт — только предупреждение, чтобы будущее добавление полей в
  одном приложении не ломало импорт в другом.

### Семантика Merge / Replace / Double при импорте существующего трекера

Портируется из `TrackerMergeBlock.tsx` веб-версии один в один:

- **Replace** — если в приложении уже есть трекер с тем же `meta.id`,
  импортированный файл полностью его заменяет (старые данные удаляются).
- **Double / Keep both** — импортированный трекер сохраняется параллельно,
  с `id`/`title` с числовым суффиксом (`Family1`, `Family2`, …), чтобы не
  конфликтовать с существующим.
- Сравнение `updatedAt` источника и получателя используется, чтобы
  подсветить пользователю, какая версия свежее (см. `isOutdated` в
  `TrackerMergeBlock.tsx`), прежде чем он выберет Replace или Double.

### Что это меняет в плане работ (шаг 8)

Слой `data/io` должен содержать:
- `TrackerFileDto` (kotlinx.serialization data classes), зеркалящий JSON
  один в один — отдельно от Room-сущностей.
- Маппер `TrackerFileDto ⇄ Room entities` с пересчётом id тегов/записей по
  правилам выше (в обе стороны).
- Юнит-тесты на маппер с реальными файлами, экспортированными из веб-версии
  (взять образцы прямо из `../expenses-tracker`), чтобы гарантировать, что
  Android действительно читает файлы веб-приложения, а не только свои же.

## Явно не в скоупе (пока)

- Синхронизация между устройствами (кроме ручного экспорта/импорта файла).
- Десктопная версия — рассматривается отдельно после Android
  (Kotlin Multiplatform + Compose Desktop, если Android-версия оправдает подход).
- Публикация в Google Play — сборка `.apk` для side-load достаточно для начала.
